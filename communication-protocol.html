How an analyzer's result becomes an HL7 message

HL7 v2 is plain text. Every lab result your analyzers send to a LIS is a few lines of it. Once you can read those lines, you can debug an interface, check a mapping, and start writing your own parser.

Anatomy of a message

HL7 v2 is a set of boxes inside boxes. Each level is cut apart by one special character. Learn five characters and you can split any message.

  1. CR

    Message to segments

    Each segment is one line. The line ends with a carriage return (CR, byte 0x0D), not the usual newline.

    PID|1||HN12345||Jaidee^Somchai||19800115|M OBR|1|ORD001|SID001|CBC^Complete Blood Count|||20260919093000
  2. |

    Segment to fields

    The pipe splits a segment into fields. A field's meaning comes from its position, so an empty field still keeps its place: || is not a typo.

    OBX|2|NM|HGB^Hemoglobin||9.1|g/dL|13.0-17.0|L|||F
  3. ^

    Field to components

    A field can hold several related parts. Here the test code comes first and the readable name second.

    HGB^Hemoglobin
  4. &

    Component to sub-components

    One more level down. Rare in lab results, but it is in the standard.

  5. ~

    Repeating a field

    The tilde repeats the same field, such as two phone numbers for one patient.

    0812345678~0298765432
  6. \

    Escape

    When data itself contains a special character, the sender writes it as a code between backslashes. \S\ means ^, \F\ means |, \T\ means &, \R\ means ~, \E\ means \.

    10\S\3/uL is read as 10^3/uL

The five characters are declared in MSH-1 and MSH-2 at the top of every message: | and ^~\&.

Receiving an order

An order message uses the same building blocks as a result. The difference is intent: it asks for work instead of reporting it. This one goes from the HIS to the LIS. Click through it the same way.

The receiver answers an order with an ACK too (ACK^O01 for this message).

ORC-1: what to do with the order

The ORC segment sits before OBR and tells the receiver what to do with the order. This is how a cancel or a change reaches the lab.

ORC-1MeaningWhat the LIS does

How the analyzer gets the order

The order also has to travel one more hop, from the LIS down to the analyzer. This happens only when the analyzer is set to bidirectional (host query) mode.

  1. The operator loads the tube and the analyzer reads its barcode.
  2. The analyzer sends a host query to the LIS containing the sample ID.
  3. The LIS looks up that sample ID and replies with the patient details and the tests ordered.
  4. The analyzer runs only those tests. If it gets no order back, it cannot match the tube and shows an error.

The exact fields of the query and reply differ between analyzer models, so I show no fixed layout here. Expect three things in the reply: the sample ID, who the patient is, and which test codes to run. The test codes must be mapped between LIS and analyzer, and a missing or wrong mapping is the most common reason for wrong or missing tests.

The reply: ACK

Every message expects an answer. The receiver sends back an ACK, a short message of two segments. Click through it the same way.

Where interfaces go wrong

Most HL7 problems on site come from a short list.

Line endings

Segments end with CR, but many editors and logs expect LF. A raw message can look like one long line in Notepad. In code, split on both.

MSH counts differently

MSH-1 is the pipe itself, so after you split MSH on |, list index 1 is MSH-2. For MSH the list index is the field number minus 1. For every other segment they are equal.

Empty fields hold their place

Never drop empty fields when parsing. If you do, every field after it shifts by one and the results land in the wrong place.

Special characters in units

The unit 10^3/uL contains the component separator. Senders either write 10*3/uL or escape it as 10\S\3/uL. If your LIS shows odd units, check this first.

Thai text and character sets

MSH-18 says which character set the message uses, for example UNICODE UTF-8. If sender and receiver disagree, Thai patient names arrive garbled.

One stream, many messages

TCP is a stream of bytes with no message boundaries. MLLP framing marks them: each message starts with byte 0x0B and ends with 0x1C then 0x0D. Without the frame the receiver cannot tell where one message stops.

Version and vendor differences

Field layouts and message types vary between HL7 versions and between analyzer models. Check the analyzer's HL7 interface manual and the LIS interface specification before assuming a field.

The same idea in Python

This is the whole parser. Notice there is no library: an HL7 message is text, and text can be split.

raw = r"""MSH|^~\&|MINDRAY|LAB|LIS|HOSP|20260919101500||ORU^R01|MSG00001|P|2.3.1
PID|1||HN12345||Jaidee^Somchai||19800115|M
OBR|1|ORD001|SID001|CBC^Complete Blood Count|||20260919093000
OBX|1|NM|WBC^White Blood Cell||7.2|10*3/uL|4.0-10.0|N|||F
OBX|2|NM|HGB^Hemoglobin||9.1|g/dL|13.0-17.0|L|||F"""

segments = raw.replace("\r", "\n").split("\n")   # CR in real messages

for line in segments:
    f = line.split("|")              # f[0] is the segment name
    if f[0] == "PID":
        family, given = f[5].split("^")
        print("Patient:", given, family, "HN:", f[3])
    elif f[0] == "OBX":
        code, name = f[3].split("^")
        print(f"{name}: {f[5]} {f[6]}  ref {f[7]}  flag {f[8]}")

Three things to notice. r"""...""" is a raw string, so Python leaves the backslash in ^~\& alone. f[5] works because for PID the list index equals the field number. .split("^") then cuts the field into components.
